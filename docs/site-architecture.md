# Site Architecture

The newsletter is published as a static Astro 5 site with components for featured items, tag browsing, monthly archives, and full-text search (Pagefind). This document describes the site's structure, component patterns, content architecture, and development workflows.

## Content Model

### Issue file format

Issue files live at `site/src/content/issues/<edition>/YYYY-MM-DD.md` (populated by the daily pipeline on the `content` branch, then deployed by the workflow to the site build). Each file contains frontmatter (YAML) describing the issue structure and metadata.

The frontmatter schema includes:
- `date` (YYYY-MM-DD format; also used as the issue slug)
- `theme` (optional 1–2 sentence summary for front-page card copy)
- `featured` (array of featured items with full metadata: id, section, source, url, title, author, score 0-10, tags, prose summary, optional takeaway/question)
- `appendix` (object with papers/news/blogs arrays; items are uncertain scores; structure is title + url only)
- `metadata` (items considered, counts by section, cost_usd, duration_seconds)

### Content schema validation

The content collection schema is defined in `site/src/content.config.ts`. Astro loads and validates every issue at build time using Zod:

1. **Edition exists**: the first path segment (edition slug) must match an entry in `editions/*/edition.yaml` on `main`.
2. **URL scheme safety**: all item URLs are verified to use `http://` or `https://` (second line of defense; `fetch.py` validates first, this schema validates second).
3. **Item structure**: featured items, appendix items, and metadata are validated against strict schemas (no unknown fields, required fields present, types correct).

If any issue file violates the schema, the build fails loudly with the file path and error message. The last-good site remains live until the next successful push.

## Components

### Component patterns

All components are **Astro components** (`.astro` files). They use Astro's island architecture: components are server-side rendered to HTML by default, with optional `client:*` directives for interactivity.

**Props interface:**

```astro
---
interface Props {
  item: FeaturedItem;
  edition: string;
}
const { item, edition } = Astro.props;
---
<article>...</article>
<style>...</style>
```

**Inline markdown rendering with XSS protection:**

The `FeaturedItem` component renders LLM-generated summaries as inline Markdown (to support **bold**, `code`, links). Because this content is untrusted, it is sanitized:

1. **marked.parseInline()** converts Markdown to HTML.
2. **DOMPurify.sanitize()** strips any dangerous tags and attributes, allowing only: `<strong>`, `<em>`, `<code>`, `<a>`, `<br>`.

This two-stage pipeline prevents XSS from prompt-injected or feed-sourced content (see security issue #248).

### Key components

| Component | Purpose |
|-----------|---------|
| **BaseLayout** | Page shell: nav, footer, metadata (title, description, og tags) |
| **FeaturedItem** | Item card: title link, source, author, score bar, tags, prose summary, optional takeaway/question |
| **AppendixSection** | Collapsible section for uncertain items (score 4-6 or dropped); shows titles + sources |
| **TagChip** | Clickable tag label with edition-aware link |
| **ScoreBar** | Visual bar 0-10 (score colors: red ≤3, yellow 4-6, green 7-10) |
| **Callout** | Styled container for takeaway (💡) or open_question (❓) |
| **MonthView** | Grid of day cards for a month archive (grayed-out days with no issues) |
| **Search** | Pagefind search widget; only functional after `pnpm build` |

## Pages and Routing

### Dynamic routes and parameters

Astro uses `[bracket]` syntax for dynamic segments. A route like `[edition]/issues/[date].astro` generates pages for every `(edition, date)` pair present in the content collection.

| Route | Template | Generates |
|-------|----------|-----------|
| `/` | `index.astro` | Edition picker (home page) |
| `/<edition>/` | `[edition]/index.astro` | Edition archive (list of all issues) |
| `/<edition>/issues/<date>/` | `[edition]/issues/[date].astro` | Single issue (featured + appendix) |
| `/<edition>/tags/` | `[edition]/tags/index.astro` | Tag cloud (all tags for edition) |
| `/<edition>/tags/<tag>/` | `[edition]/tags/[tag].astro` | Tag archive (all items tagged `<tag>`) |
| `/<edition>/months/<yyyymm>/` | `[edition]/months/[yyyymm].astro` | Month archive (all issues in month) |
| `/<edition>/rss.xml` | `[edition]/rss.xml.js` | RSS feed (per-edition) |
| `/rss.xml` | `rss.xml.js` | Root RSS (copy of `/agents/rss.xml`) |
| `/<edition>/search` | `[edition]/search.astro` | Search page (Pagefind widget) |

### Home page (`index.astro`)

- Lists all visible editions (hiding drafts unless `SHOW_DRAFTS=1`).
- For each edition, shows: name, tagline, latest issue date and theme, issue count, links to archive and RSS.
- Editions are sorted by `order`, then by slug.

### Issue page (`[edition]/issues/[date].astro`)

- Renders one complete issue: theme header, featured items grouped by section (papers, news, blogs), appendix, footer metadata.
- Sections are rendered only if they have items (no "## Papers" header with zero papers).
- Sets page title and metadata for social sharing.

### Tag pages (`[edition]/tags/[tag].astro`)

- Lists all items tagged `<tag>` across all dates in the edition.
- Tag slugs are normalized (lowercased, special chars removed; see `tag-slug.ts`).
- Links back to the tag cloud.

### Month archive (`[edition]/months/[yyyymm].astro`)

- Grid of day cards (7-column calendar).
- Days with no issue are grayed out; days with issues link to the issue page.
- Months are zero-filled (e.g., `2026-01`) so URL sorting works correctly.

## Scripts and Utilities

### Edition registry (`editions.ts`)

Key exports:

- `parseEdition(yaml: string, slug: string): Edition` — Parse edition.yaml from main branch (must exist; no optional fields)
- `readEditions(editionsDir: string): Edition[]` — Load all editions from disk
- `loadRegistry(): Registry` — Load and cache the registry (called at build time)
- `listEditions(all: Edition[], showDrafts: boolean): Edition[]` — Filter visible editions (hide drafts unless SHOW_DRAFTS=1)
- `issuesFor(allIssues, editionSlug): Issue[]` — Extract issues belonging to an edition
- `unknownContentEntries(dirListing, knownEditions): string[]` — Validate no stray content entries outside known editions

Edition object:
```typescript
{
  slug: string;        // lowercase, no spaces; permanent; in URL
  name: string;        // display name
  tagline: string;     // short 1-line description
  status: 'live' | 'draft' | 'paused';
  order: number;       // sort order (lower = first); used on home page
}
```

### Tag slug utility (`tag-slug.ts`)

Normalizes tags for URL safety (lowercased, special chars removed):

```typescript
tagSlug("Tool-Use") → "tool-use"
tagSlug("Multi-Agent") → "multi-agent"
```

### URL scheme validation (`safe-href.ts`)

Validates item URLs before rendering them as `<a href>`:

```typescript
safeHref(url: string): string
// Returns url if it uses http:// or https://; otherwise returns "#" (safe fallback)
```

This is a second line of defense after `fetch.py` already validates URLs (the content schema adds a third).

### Month utilities (`months.ts`)

Key exports:

- `parseMonth(yyyymm: string): [number, number]` — Return (year, month) tuple from YYYY-MM string
- `daysInMonth(year: number, month: number): string[]` — Return array of day strings for a month (zero-filled)
- `groupByMonth(issues): Map<string, Issue[]>` — Group issues by month

### RSS helpers (`feed.js`)

Generates RSS 2.0 feeds (XML) for each edition:

- Feed metadata (title, link, description, lastBuildDate)
- Item entries: title, link, description, pubDate, author
- Per-section RSS files and a combined RSS for the edition

## Testing

### Test infrastructure

Tests use **Vitest** (Node.js test runner, Jest-compatible API). They run on every PR and push to `main` via `.github/workflows/site-tests.yml`.

```bash
# Run all site tests
pnpm --prefix site test

# Run in watch mode (reruns on file changes)
pnpm --prefix site test --watch

# Run a specific test file
pnpm --prefix site test -- editions.test.ts
```

### Test patterns

**1. Edition registry** (`editions.test.ts`)

Tests edition YAML parsing, validation, and listing:
- Parse valid edition YAML
- Reject invalid configs (bad status, slug mismatch, missing required fields)
- Listing hides drafts (unless `SHOW_DRAFTS=1`), keeps paused, sorts by order + slug

**2. Content validation** (`content-url-scheme.test.ts`)

Tests URL scheme safety (http/https only, no data: or javascript:).

**3. Page rendering** (`issue-page.test.ts`, `index-page.test.ts`, `tag-pages.test.ts`)

Uses seed editions to generate mock content, then:
- Imports Astro pages as functions and calls them with `{ params, props }`
- Asserts HTML output contains expected structure and metadata

**4. Component rendering** (`featured-item.test.ts`, `appendix-section.test.ts`, `tag-chip.test.ts`)

Tests component output (HTML structure, CSS classes, inline markdown rendering and XSS protection).

**5. RSS generation** (`rss.test.ts`)

Parses generated RSS XML and verifies:
- Feed metadata (title, link, description)
- Item entries (title, link, description, pubDate)
- Per-edition feeds and root RSS are valid

**6. Multi-edition layout** (`multi-edition.test.ts`)

Tests that multiple editions coexist correctly:
- No content leakage between editions
- Edition picker shows all editions
- Tag pages are per-edition (same tag in different editions are separate)

**7. Search integration** (`search.test.ts`)

Tests that the Pagefind widget is present on search pages and properly configured.

### Seed editions

Tests use a fixture generator (`seed-editions.ts`) to create mock edition configs and issues without touching the filesystem. This makes tests fast and deterministic.

## Build and Deploy

### Local build

```bash
# Full build (Astro compile + Pagefind indexing)
pnpm --prefix site build

# Build output
site/dist/
├── index.html
├── [edition]/
│   ├── index.html
│   ├── issues/
│   ├── tags/
│   ├── months/
│   └── search/
│       └── index.html
└── pagefind/
    ├── pagefind.js
    ├── pagefind-ui.js
    └── index/
```

### Preview locally

```bash
# Serve built output (useful for testing search; dev mode doesn't run pagefind)
pnpm --prefix site preview
```

### Deploy workflow (`.github/workflows/deploy.yml`)

1. Triggers on push to `main` or `content` branch
2. Checks out `main` (primary tree: site scaffold, config, `package.json`)
3. Fetches `content` branch into `_content/` (one-time fetch, not a git worktree)
4. Copies issue files from `_content/editions/*/issues/` → `site/src/content/issues/*/`
5. Runs `pnpm install && pnpm run build`
6. Deploys `dist/` to GitHub Pages

**Build gate:** If the build fails (bad content, invalid schema, Astro error), the workflow fails and the last-good deploy stays live. Nothing is published until the next successful build.

## Common Development Tasks

### Preview an issue locally before it publishes

Before the daily pipeline writes and pushes an issue file to `content`:

1. Manually create a test issue file in `.worktrees/content/site/src/content/issues/agents/2026-06-29.md`
2. Include valid frontmatter with featured items, appendix, and metadata
3. Run `pnpm --prefix site dev` and navigate to http://localhost:3000/agents/issues/2026-06-29/

### Add a new component

1. Create `site/src/components/MyComponent.astro` with a Props interface
2. Implement the component markup, styles (scoped with `<style>`), and logic
3. Import and use on a page: `import MyComponent from "../components/MyComponent.astro";`
4. Add a test in `site/tests/my-component.test.ts`

### Modify a page route

1. Edit the `.astro` file in `site/src/pages/`
2. Use `[bracket]` syntax for dynamic segments
3. Test by running `pnpm --prefix site dev` and navigating to the page

### Add a new tag to the tag cloud

Tags are automatically collected at build time from `featured[].tags` in issue files. To add a tag:

1. Edit the issue file in `.worktrees/content/site/src/content/issues/<edition>/YYYY-MM-DD.md`
2. Add the tag to an item's frontmatter `tags: [new-tag]`
3. Rebuild — the tag will appear in the tag cloud on the next build

### Debug a page build failure

When Astro fails to build:

1. Look at the error message — it usually names the issue file that failed
2. Check the issue file frontmatter:
   - Is the YAML valid?
   - Are required fields present: `date`, `featured`, `appendix`, `metadata`?
   - Are item URLs valid (http/https only)?
3. Check the edition:
   - Does the edition exist in `editions/*/edition.yaml` on `main`?
   - Is the edition `status: live` (or `SHOW_DRAFTS=1` for drafts)?
4. Check for component issues:
   - Are components imported correctly?
   - Are all props passed correctly?

### Test search locally

Pagefind indexing only runs during `pnpm build`, not in dev mode:

```bash
pnpm --prefix site build && pnpm --prefix site preview
```

### Show draft editions in dev

By default, draft editions are hidden. To show them:

```bash
SHOW_DRAFTS=1 pnpm --prefix site dev
```

Draft editions are always hidden in the deployed site unless explicitly built with `SHOW_DRAFTS=1`.

## Performance Notes

- **Pre-rendering all pages** keeps response times sub-100ms (GitHub Pages CDN)
- **Pagefind indexing** adds ~5–10 seconds to the build; search is instant client-side
- **Content versioning** on the `content` branch means old issues remain queryable forever

## Frequently Asked Questions

**Q: Why is search not working in `astro dev`?**

A: Pagefind indexing only runs during `pnpm build`. For local search testing, run `pnpm --prefix site build && pnpm --prefix site preview`.

**Q: How do I debug a page build failure?**

A: Look at the build error message — it usually names the issue file that failed. Common causes:
- Issue file frontmatter is invalid YAML
- An issue file exists but its edition is not in `editions/*/edition.yaml` or has `status: draft` (and `SHOW_DRAFTS` is not set)
- A component is importing from Astro unsafely (must be in the `---` script block)

**Q: Can I run just one test?**

A: Yes: `pnpm --prefix site test -- editions.test.ts`

**Q: How do draft editions appear on the site?**

A: By default, draft editions are hidden. To show them in local dev:
```bash
SHOW_DRAFTS=1 pnpm --prefix site dev
```

**Q: What happens if the content collection schema validation fails?**

A: The build stops with a clear error message. The last-good site stays live until the next successful deploy. Fix the issue file and re-push to trigger a rebuild.

**Q: Can I customize the site styling?**

A: Global styles live in `site/src/styles/global.css` (design tokens, reset, typography). Component-scoped styles are in each `.astro` file's `<style>` block. Both use CSS variables for theming.
